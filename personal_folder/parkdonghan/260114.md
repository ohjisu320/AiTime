# AI 서비스에서 Jenkins로 CI/CD를 설계하는 법

### — “PR 만들면 자동으로 검증되고, 머지되면 안전하게 배포되는 흐름”을 한 번에 연결하기

AI 서비스를 만든다는 건, 모델을 한 번 잘 학습시키는 것에서 끝나지 않는다.
로컬에서 모델이 잘 돌아가고 FastAPI로 `/predict` 엔드포인트까지 만들었다고 해도, 운영을 시작하면 이상하게 문제가 터진다.

* PR은 머지됐는데 테스트는 안 돌았고
* 누군가 서버에 들어가 수동으로 배포하다가 실수를 하고
* “지금 운영 중인 코드/모델 버전이 뭐였지?”를 아무도 정확히 말하지 못하고
* 의존성 취약점은 어느 날 갑자기 폭발한다.

따라서, 이 글은 그 혼란을 “구조”로 해결하는 방법을 다룬다.

**CI/CD → 파이프라인 → 오케스트레이션 → Jenkinsfile → Controller/Agent → FastAPI 배포 → AI/MLOps(CT까지)**

이 흐름에 대해 나름의 연결성을 바탕으로 설명하겠다!!

---

## 1) CI/CD는 왜 필요해졌을까?

팀이 작고 변경이 적을 때는 이렇게도 된다.

1. 기능 추가
2. 알아서 테스트
3. 서버 들어가서 배포
4. 잘 되면 다행

하지만 변경이 잦아지는 순간 이 방식은 바로 깨진다.
문제는 “개발자가 못해서”가 아니라 “사람이 반복 작업을 안정적으로 못해서” 생긴다. 휴먼 에러인 것이다.

* 통합이 늦어질수록 충돌이 커지고
* 배포가 사람 손에 의존할수록 실수가 늘고
* 릴리즈가 느려질수록 피드백이 늦고

그래서 등장한 것이 **CI/CD**다.

* **CI(Continuous Integration)**:
  PR/커밋이 올라올 때 자동으로 빌드/테스트/정적검사를 돌려 “merge 가능한 상태”를 만든다.
* **CD(Continuous Delivery/Deployment)**:
  merge된 결과물을 자동으로 배포하고, 배포 후 검증/관측/롤백까지 포함해 “안전한 릴리즈”를 만든다.

> “그럼 이렇게 자동으로 돌아가는 과정은 도대체 어디에 정의돼? 누가 실행해?”

이 질문을 해결하려면 **파이프라인**이 필요해진다.

---

## 2) 파이프라인은 CI/CD를 ‘실행 가능한 단계’로 바꾼 것이다

CI/CD는 개념이고, 실제로는 “단계들의 흐름”으로 구현된다.

예를 들어 PR에서 CI 파이프라인을 돌린다면:

1. Checkout
2. Lint/Format(ruff/black/flake8 등)
3. Test(pytest)
4. SAST(정적 보안 분석)
5. Dependency scan(취약한 라이브러리 탐지)

merge 후 CD 파이프라인을 돌린다면:

6. Build(예: Docker image, 또는 Python wheel)
7. Push(레지스트리에 업로드)
8. Deploy(서버에 적용)
9. Health/Smoke test(정상 동작 확인)
10. 실패 시 rollback + 알림

여기서 artifact와 registry도 함께 잠깐 보자.

* **artifact**: 빌드 결과물(도커 이미지, wheel, 모델 파일, 리포트 등)
* **registry**: 그 결과물을 저장해두는 저장소(Docker Registry/ECR 등)
  *(메모리 레지스트리 같은 개념이 아니라 “저장소 서비스”를 말한다.)*

그런데 파이프라인을 만들고 나면 바로 이런 의문이 생긴다.

> “PR에서도 배포까지 하면 안 되잖아?
> 실패하면 재시도해야 하고, 배포는 동시에 하면 충돌 나고, 롤백도 해야 하는데?”

즉 “단계 목록”만으로는 부족하고, **실행 규칙**이 필요하다.
이게 오케스트레이션으로 넘어가는 이유다.

---

## 3) 파이프라인 vs 오케스트레이션: 과정과 운영 제어를 분리해 이해하기

헷갈리지만 딱 이렇게 보면 된다.

* **파이프라인**: “무엇을 어떤 순서로” (공정표/레시피)
* **오케스트레이션**: 그 공정표를 실행할 때 “어디서/언제/조건/실패 처리”를 적용하는 운영 제어

예를 들어:

* PR이면 Deploy 단계는 스킵
* main 브랜치면 배포 허용
* docker push가 잠깐 실패하면 retry(3)
* 10분 넘게 걸리면 timeout으로 실패 처리
* 배포는 동시에 1개만(락/큐)
* 실패하면 rollback.sh 실행 + Slack 알림
* GPU 필요한 단계는 GPU 라벨 Agent에서만 실행

이 오케스트레이션이 “상황에 맞춰 유기적으로 움직이는 것처럼” 보이지만,
즉흥이 아니라 **미리 정의한 정책대로** 움직이는 것이다.

> “그렇다면 그 과정과 규칙을 어디에 적어두고, 누가 읽어서 실행해?”

이 질문이 바로 **Pipeline as Code**로 연결된다.

---

## 4) Jenkinsfile(Pipeline as Code): 파이프라인도 코드처럼 관리하자

파이프라인을 Jenkins UI에서 클릭으로 만들 수도 있다.
하지만 실무에서는 대체로 “클릭 파이프라인”이 사고를 부른다.

* 누가 언제 뭘 바꿨는지 추적이 어렵고
* 리뷰 없이 운영 정책이 바뀌고
* 프로젝트마다 복붙되어 표준이 깨진다

그래서 파이프라인을 **repository에 파일로 둔다.**

* Jenkins: `Jenkinsfile`
* GitHub Actions: `.github/workflows/*.yml`

이 둘은 철학이 같다.
“파이프라인도 코드니까 버전관리하고 PR로 리뷰하자.”

그런데 여기서 또 하나의 혼동이 생긴다.

> “GitHub Actions는 GitHub에서 알아서 도는 느낌인데, Jenkins도 GitHub가 돌려줘?”

정답은 아니다. Jenkins는 **별도의 서버**에서 돈다.

## 5) Jenkins는 어디에서 돌아가고, 왜 Controller/Agent로 나누나?

Jenkins는 GitHub 기능이 아니라, **내가(회사/팀이) 띄워둔 Jenkins 서버**다.

* GitHub는 PR/push event를 웹훅으로 Jenkins에 알려준다(트리거)
* Jenkins는 그 event를 받아 실제 파이프라인을 실행한다

그리고 Jenkins는 보통 **Controller/Agent 구조**로 운영한다.

* **Controller**: 파이프라인 스케줄링/관리, 웹 UI, 권한, 크리덴셜 관리(지휘자)
* **Agent**: 실제 명령을 실행하는 작업 머신(작업자)

그래서 EC2를 2대 쓰는 구조가 흔하다.

* EC2 #1: Jenkins Controller
* EC2 #2: Jenkins Agent

왜 분리하냐?

1. **안정성**: 빌드가 무거우면 Controller까지 죽으면 전체가 멈춘다
2. **확장성**: Agent만 늘리면 병렬 빌드 가능
3. **보안**: 코드 실행 영역(Agent)과 관리 영역(Controller)을 분리해 사고 반경을 줄인다

여기서 하나 더 중요한 포인트가 있다.

> Jenkinsfile에 모든 것이 들어가지 않는다.

예를 들어,

* 어떤 Agent가 있는지(라벨/스펙/개수)
* 크리덴셜(시크릿) 값 자체
* 권한/RBAC/플러그인 정책

이런 건 Jenkinsfile이 아니라 Jenkins 관리 영역에 둔다.
이유는 간단하다: **보안과 운영 통제** 때문이다.

* **Secrets**는 민감정보 전체(API 키, 비밀번호 등)
* **Credentials**는 그중 “접근 인증 정보”(SSH 키, 토큰 등)

Jenkinsfile에는 값이 아니라 “ID로 참조”만 하는 것이 표준이다.

## 6) 그럼 Jenkins 2대와 FastAPI는 어떻게 연결될까?

여기서 많은 사람이 착각한다.

> “Agent에 FastAPI가 돌아가나요?”

보통은 아니다.

* **FastAPI는 ‘서빙 서버(프로덕션 EC2)’에서 상시 실행**
* **Jenkins Agent는 ‘배포 시점에만’ 서버를 교체**

즉, 관계는 이렇게 된다.

* Controller: “파이프라인 시작/규칙 적용”
* Agent: “빌드/푸시/배포 명령 실행”
* FastAPI 서버: “실제 트래픽 처리”

가장 흔한 흐름은 이렇다.

1. Agent가 Docker 이미지를 빌드
2. ECR(또는 GHCR) 같은 Docker Registry에 push
3. Agent가 FastAPI 서버에 SSH/SSM으로 접속
4. FastAPI 서버에서:

   * docker pull 새 이미지
   * docker compose up -d 로 교체
5. Agent가 `/health`로 헬스체크 + `/predict`로 스모크 테스트
6. 실패 시 rollback + 알림

여기서 CD의 진짜 의미가 드러난다.

CD는 “올려!”가 아니라 **“올리고, 정상 확인하고, 실패하면 되돌려!”**다.

## 7) CD를 안전하게 만드는 장치들: 스테이징/배포전략/롤백/모니터링

### 스테이징 vs 프로덕션

* **staging**: 운영과 유사한 검증 환경
* **production**: 실제 사용자 트래픽 환경

안전한 운영은 보통:

* 스테이징에서 먼저 배포/검증
* 통과하면 프로덕션으로 승격

### 배포 전략(rolling / blue-green / canary)

* **rolling**: 하나씩 순차 교체
* **blue-green**: 두 환경을 준비해 스위칭
* **canary**: 일부 트래픽만 신규로 보내 점진 확대

### 헬스체크 / 스모크 테스트

* 헬스체크: “살아있나?” (`/health`)
* 스모크 테스트: “최소 기능이 동작하나?” (`/predict` 더미 입력 200)

### 관측 기반 판단 + 롤백

실제로는 배포 직후 잠깐 지켜본다.

* 에러율 급증?
* p95 지연시간 급상승?
* 메모리 폭증?

이상하면 자동 롤백한다.

이제 여기서 “빨리 실패 잡기”로 연결된다.
왜냐면 배포까지 가는 시간은 비싸니까.

## 8) Fail Fast: 파이프라인을 빠르게 실패시키는 설계 기준

Fail Fast는 단순한 슬로건이 아니라 **비용 절감 전략**이다.

* 가장 빠르고 값싼 검사부터 앞에: lint → unit test → build → deploy
* 실패 가능성이 높은 걸 앞에
* 무거운 작업(대형 통합테스트, AI 학습)은 게이트 통과 후
* retry/timeout을 명확히

그리고 속도를 끌어올리는 핵심이 **캐시 전략**이다.

* pip/poetry 캐시: 의존성 설치 재사용
* Docker layer 캐시: 레이어 재사용(의존성 설치는 앞에, 소스 복사는 뒤에)
* model artifacts 캐시: 모델/토크나이저 같은 대용량 파일 버전 저장(S3 등)

이런 최적화가 들어가야 “PR마다 자동화”가 현실적으로 가능해진다.

## 9) PR 만들면 무엇이 자동으로 되고, 배포까지 최종 과정은?

### PR 생성/업데이트(=CI)

1. GitHub 이벤트 발생 → Jenkins 트리거
2. Agent가 checkout
3. ruff/black, pytest, SAST, dependency scan
4. 결과가 PR Checks로 표시
5. 통과해야 merge 가능(팀 정책)

### main merge(=CD)

1. main 커밋 기준으로 빌드/테스트
2. 도커 이미지 생성(태그는 git sha로 추적 가능)
3. 레지스트리에 push(ECR)
4. 스테이징 배포 → 검증(헬스/스모크)
5. 프로덕션 배포(승인 게이트를 둘 수도 있음)
6. 모니터링 지표 확인
7. 실패 시 롤백 + 알림

여기까지가 “웹서비스 CI/CD”인데, AI에서는 하나가 더 붙는다.

> “AI는 모델이 바뀌잖아. 그럼 모델도 같은 방식으로 관리해야 하지 않아?”

이 질문이 MLOps로 이어진다.

## 10) AI에서 CI/CD는 “코드 + 모델”이다 (+ CT까지)

AI에서 배포 대상은 두 덩어리다.

* **서빙 시스템**: FastAPI 코드 + 컨테이너 + 환경설정
* **모델 artifact**: 학습된 모델 파일 + 토크나이저/전처리 리소스

그래서 저장소 개념이 중요해진다.

### S3 / ECR / MLflow의 역할 분리

* **S3**: 파일 창고(모델 파일/데이터/리포트)
* **ECR**: 컨테이너 이미지 창고(서빙 앱)
* **MLflow Model Registry**: 모델 버전/승격(Production/Stage)/메타데이터 관리

ECR은 모델 레지스트리가 아니라, **이미지 레지스트리**다.
모델을 이미지 안에 포함시켜 저장할 수는 있지만 “모델 승격/Lineage”는 MLflow 같은 도구가 맡는 편이 편할 수 있다.

그리고 모델은 운영 중에 성능이 떨어질 수 있다.

* 입력 분포가 바뀐다(드리프트)
* 데이터 라벨이 쌓이며 성능이 하락한다
* 환경이 변해 개념 드리프트가 생긴다

이때 등장하는 것이 **CT(Continuous Training)**다.

### 드리프트/성능저하 → 자동 재학습(CT)

* 드리프트 신호 감지(입력 분포 변화, 예측 분포 변화 등)
* 또는 라벨 기반 지표 하락 확인
* 자동 재학습 실행(from scratch / warm-start / 재-finetune)
* 후보 모델 평가 후 “베스트 모델” 자동 선정
* 레지스트리에 등록/승격
* CD로 교체 배포(모델만 바꾸거나, 코드+모델 함께)

그리고 여기서 Jenkins의 역할이 다시 명확해진다.

> Jenkins는 모델을 학습시키는 도구가 아니라,
> 학습/평가/등록/배포를 **파이프라인으로 연결해 오케스트레이션**하는 도구다.

---

## 11) FastAPI vs BentoML: 치환 가능한가?

서빙 레이어 관점에서 보면

* FastAPI도 추론 API를 만들 수 있고
* BentoML도 모델 서빙에 특화된 방식으로 API를 만든다

그래서 “치환 가능”은 맞지만, 성격은 이렇게 다르다.

* FastAPI: 범용 웹 프레임워크(서빙 외 기능도 많을 때 좋음)
* BentoML: 모델 서빙/패키징 중심(모델 중심 운영 흐름에 강점)

현실적으로는:

* 단순 추론 API면 BentoML로 대체 가능
* 제품 API가 많으면 FastAPI 유지 + 모델 서빙만 분리(BentoML)도 가능

## 마무리: Jenkins의 핵심은 “자동화”가 아니라 “연결”이다

흐름을 정리하면 다음과 같다

**CI/CD → 파이프라인 → 오케스트레이션 → Jenkinsfile → Controller/Agent → FastAPI 배포 → MLOps(CT)**

* 사람 손의 불안정성을 줄이려면 CI/CD
* CI/CD를 실행하려면 파이프라인
* 파이프라인을 운영하려면 오케스트레이션
* 오케스트레이션을 관리하려면 Jenkinsfile
* Jenkinsfile을 돌리려면 Controller/Agent
* 운영 서비스와 연결되면 배포/헬스/롤백
* AI는 모델이 움직이니 레지스트리/드리프트/CT
